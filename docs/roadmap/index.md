# Roadmap — Features in Planning

This section contains implementation plans for features that have been fully researched and architecturally specified but are not yet implemented. Each page captures the design intent, API surface, error model, and key decisions so that implementation can start without re-doing the research.

These are **living design documents** — they reflect the current best thinking at the time of writing. API surface may change slightly during implementation as new constraints are discovered.

TWO ATTACHMENT POINTS resolve a sequencing bug (spec generation freezes at `.Register(builder)`, before a transport-layer-attached middleware could ever influence it): spec-relevant middleware (carrying a `Security`/`RequestParams`/`ResponseParams` declaration) attaches via a NEW `rest.WithMiddleware` `RouteOpt` at `NewRoute(...).Register(builder)` time — EARLY enough to feed the OpenAPI spec directly, so a route needs ZERO manual `WithSecurityScheme`/`RouteMeta.Security`/header-param calls; non-spec/shared middleware (observability, logging) stays attachable at `nethttp.Register(...)`'s variadic parameter, unchanged. This is NOT the previously-rejected "infer from attached middleware" — the middleware VALUE carries a COMPLETE, EXPLICIT declaration (scheme, scopes, codec, via ordinary constructor arguments); attaching it IS declaring it, cross-checked for conflicts (`ConflictingSecurityDeclarationError`) against the still-supported manual escape hatch. Security `Fn` is Req-generic AND POINTER (`*Req`) — reads AND WRITES the already-merged struct, closing a "declare twice" gap; `codex.DecodeVars`/`RequiredField`/`OptionalField` let a middleware decode via ITS OWN dedicated codec with zero new `codex` API (with an explicit guardrail: a VERIFYING codec must never be wired through a route-declared merge field — it renders the WRONG OpenAPI schema, confirmed via `codex.StringValidatorFrom`). New `middleware.ContextField[V]` — a codec-typed ctx value bus mirroring `WithResponseHeaders`/`stats.WithObserver` — is the default recommendation for TRULY cross-cutting data (keeps Req/Resp security-agnostic). Response-side header/cookie forwarding already works via existing `WithResponseHeaders`/`WithResponseCookies`; `ResponseParams` adds the spec-declaration half. Observability: `stats.Observer` splits into boundary-shaped (moves to middleware, zero loss) vs. decode-intrinsic (`RecordValidationError`, resolved via a new `stats.Diagnostic` ctx-ferry) — `nethttp.Observability` becomes the sole remaining `stats.Observer` call site, `Options.Observer` REMOVED. Will get a dedicated `docs/concepts/middleware.md` + `docs/features/middleware.md` doc pair once implemented. **Coverage confirmed for every LAYER 2 boundary go-codex ships** (exactly THREE attachment shapes — HTTP/message/decorator — no fourth needed anywhere): events/reqreply (`mqtt`/`mqtt5`/`zeromq`) get FULL parity with REST (message-shaped, reusing the SAME `stats.Diagnostic` ferry); MCP (`mcpgo`) gets observability-only via a decorator shape (Security stays permanently N/A, unchanged); `ports.File`/`Cache`/`SQL`/`Dir` all get the SAME decorator shape `File` already proves. Layer 3 (`forge.Registry`/pipelines) is NOT covered — see L14 below. All Phase 2+ for implementation, but no longer vague — see "Coverage across every API/port boundary" in the doc. **L1-L14 ALL RESOLVED** across three full critical review passes (see prior summaries in doc history). L12 — MCP's observability resolution used to scan `mws` for a `stats.Observer`-typed `Fn` and take the FIRST match only, silently dropping a second attached observability middleware — fixed by collecting ALL matches and combining them via the EXISTING `stats.NewFanout` (discovered during Phase 1 implementation that this fan-out helper already ships in `stats`, so no new type was needed). L13 — `middleware.ContextField[V]`'s Set/Get contract (`Set` returned a NEW ctx) was incompatible with L4's finalized security `Fn` signature (no ctx in the return tuple) — fixed by redesigning `ContextField` around a pre-allocated MUTABLE BOX in ctx (mirrors `WithResponseHeaders`' exact pattern), working uniformly from EVERY `Fn` shape and even gaining bidirectional visibility. L14 — `forge.Registry`/pipelines (Layer 3) were never checked against this design at all despite the doc's "every boundary" claim — resolved by spinning the question out into a new dedicated roadmap doc, [Forge Pipeline Middleware](forge-pipeline-middleware.md), rather than deciding inline; this doc's own coverage claim now explicitly scopes itself to Layer 2 only. See the doc's "Known limitations and open risks" section for the full, now fully-resolved punch list. |

A FOURTH pass closed that deferred question via a bigger unification: investigating a genuine, previously-undocumented nil-pointer-panic risk in `HandleMW`/`ClientMW` (`mw.Security.SchemeName` accessed with no nil guard) led to making `mw` NILABLE on both methods and REMOVING `.Implement(impl)`/`Wrap` entirely — `HandleMW(nil, fn)`/`ClientMW(nil, fn)` now cover everything those used to, with nil sanctioned as "nothing to pair against"; `Transform`/`nethttp.Observability` simplify to return the bare wrapped closure instead of a `ServerImplementation`. This closes the deferred client-side-`.Implement()`-equivalent question as a direct side effect. **A FIFTH pass — verifying this unification propagated everywhere — found and fixed 2 more items**: both fully-worked example code blocks still passed `mw` BY VALUE to `HandleMW`/`ClientMW`, a genuine compile error against the now-pointer-typed signatures, fixed via `&mw`; and `Serve`'s Part-1 gating wording was clarified so a route with `.HandleMW()` but no `.WithHandler()` is unambiguously still skipped as spec-only, exactly like a `.Use()`-only route. Zero open design questions remain — ready for implementation. See [Events/ReqReply/Ports Workflow Simplification](events-reqreply-ports-workflow-simplification.md) for the sibling doc covering the SAME pattern's implications beyond REST, and [SSE Client Consumption](sse-client-consumption.md) for SSE's client-consumption gap — both deliberately deferred until this doc's implementation ships. |

## How to read these plans

Each plan page covers:

- **Motivation** — why this feature belongs in go-codex
- **Scope decisions** — what is in and out of Phase 1
- **API surface** — exact type signatures, options structs, interface definitions
- **Structured errors** — every new error type with `slog.LogValuer` attributes
- **Observer integration** — which observer hooks fire and when
- **AsyncAPI / OpenAPI spec** — how the feature integrates with spec generation
- **Files to create** — concrete file list with responsibilities
- **Usage sketch** — end-to-end code example
