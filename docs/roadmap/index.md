# Roadmap — Features in Planning

This section contains implementation plans for features that have been fully researched and architecturally specified but are not yet implemented. Each page captures the design intent, API surface, error model, and key decisions so that implementation can start without re-doing the research.

These are **living design documents** — they reflect the current best thinking at the time of writing. API surface may change slightly during implementation as new constraints are discovered.

## Planned features

Also records will-not-implement decisions (`RetryWithBackoff`). GroupBy/Switch routing SHIPPED in `stream/route.go`; CombineLatest5+ resolved via nested composition (stream guide) |
| [AMQP 0.9.1 Adapter](amqp-adapter.md) | `adapters/amqp` | Design complete | PUB/SUB + Request/Reply over RabbitMQ — exchange/queue topology, Ack/Nack, `ReplyTo`/`CorrelationId` RPC, structured errors, observer integration |
| [TCP Adapter](tcp-adapter.md) | `adapters/tcp` | Design complete | Request/Reply + streaming over raw TCP — pluggable `FramedConn` framing, built-in length-prefix framer, stdlib-only, no CGO |
| [WebSocket — Deferred](websocket-deferred.md) | `adapters/websocket` | Deferred | Phases 1+2 SHIPPED (server adapters + `DuplexPort` + `SocketPattern`; client dial adapters with auto-reconnect + gap SocketErrors + session generations; chi variants via swapHandler delegation; `RegisterSocket` AsyncAPI channel). Remaining: `ConnectionObserver` extension, dynamic subprotocol negotiation. Will-not-implement: MQTT-over-WS, universal StreamPattern, outbound queueing across gaps |
| [Redis — Phase 2: Pub/Sub](redis-pubsub.md) | `adapters/redis` | Design draft | `SubscribeAdapter` (SourcePort) + `PublishAdapter` (SinkPort) via existing `EventPattern`; new narrow `PubSubCommands` interface + fake; at-most-once semantics documented loudly (offline subscribers LOSE messages — closer to ZeroMQ than MQTT); `PSUBSCRIBE` glob derivation from `{var}` templates; reuses `RecordSubscribe`/`RecordPublish` (no new stats extension). Redis Streams = Phase 3 candidate; still deferred from Phase 1: DelAdapter, CachePattern spec rendering. Per-var key codecs SHIPPED — see [Redis Cache Adapter](../features/redis.md#per-key-variable-codecs--portscachekeyparam) |
| [Webhook Adapter](webhook-adapter.md) | `adapters/webhook` | Design complete | `ReceiveAdapter` (SourcePort) + `DeliverAdapter` (SinkPort) — HMAC-SHA256 signature verification/signing over raw payload bytes, the one mechanism generic `nethttp`/`chi` can't do today (`SecurityFunc`/`CredentialFunc` run after body decode). Zero core changes: body-preserving verify middleware wraps `nethttp.Handler`; `handle.EncodeRequest` gives raw bytes to sign before `nethttp.Call`. Reuses `RESTPattern` (OpenAPI) + optional `EventPattern` (AsyncAPI) unchanged; retry-with-backoff mirrors `adapters/websocket`'s reconnect loop; no new stats extension (`SecurityObserver`/`Observer` reused) |
| [Fuzz & Benchmark Testing Infrastructure](fuzz-benchmark-testing.md) | `validate`, `codex`, `format` | Design complete | Internal quality initiative, no new API. Fuzz targets for every hand-rolled string/byte parser (9 `validate` regex constraints, `codex.HexColor`'s byte-level hex parser, JSON/TOML format-boundary decode) — zero fuzz targets exist today. Benchmarks for hot paths (`Struct` encode/decode, `SliceOf`/`StringMap`, `Refine` chains, `format.JSON` round trip) with `b.ReportAllocs()` — zero benchmarks exist today. New CI `fuzz` job (`-fuzztime=30s` per target); `benchstat`-comparable baseline for future regression checks |
| [Dynamic Port Rebinding (Hot-Swap Adapters)](dynamic-port-rebinding.md) | `ports` | Design draft | Live adapter cutover on running ports without process restart. Phase 1 scopes explicit `BindRef`/`Rebind`/`Unbind` on single-binding ports (`IOPort`, `DuplexPort`, `LatestPort`) with generation-based lifecycle tracking, typed `slog.LogValuer` errors, and observer reporting on all transition paths. |
| [Typed State Machine Contracts & Runtime](typed-state-machine.md) | `state`, `stream`, `forge` | Design draft | Codec-validated state payload + typed transition graph + runtime reducer so state can progress with explicit, forward-safe rules. Phase 1 includes both contract surface and runtime execution helper (no external FSM dependency). |
| [Vector Store Adapter (RAG retrieval)](vector-store-adapter.md) | `adapters/vectorstore`, `adapters/openai` (embeddings) | Awaiting use case | Placeholder for RAG's retrieval half — a narrow `VectorStore` interface (mirrors `adapters/redis.Commands`) for native vector DBs (Qdrant/Weaviate/Pinecone/Redis-search), plus the `adapters/openai` embeddings endpoint the (now-shipped) LLM Integration feature deferred. Notes what already works with ZERO new code today: pgvector similarity search via the existing generic `adapters/sql.QueryEachAdapter`, and embedding vectors via `codex.SliceOf(codex.Float32())`. Not yet designed in detail — captured as a reminder pending a concrete driving use case. |
| [OpenAI Multimodal Content](openai-multimodal-content.md) | `api/llm`, `adapters/openai` | Awaiting use case | Placeholder for image/audio/video input support — today `adapters/openai`'s wire shape is text/JSON-only (`chatMessage.Content` is always a plain string), with no path to OpenAI's multimodal `content` array (`image_url`/`input_audio` parts). Sketches a new `llm.CallOpt` for attaching media alongside the typed request codec and the `chatMessage.Content` union-type change needed on the adapter side. Not yet designed in detail — captured as a reminder pending a concrete driving use case. |
| [`PartialFrom` — Diff Two Structs Into a Patch](partial-struct-diff.md) | `codex` | Idea only | Follow-on to the now-SHIPPED Partial/Patch Struct Codec (`codex.PartialField`/`PartialStruct`, see `docs/concepts/codec.md`'s matching subsection and `.github/instructions/go-codex.instructions.md`) — auto-derive a patch by diffing a base/previous `T` against an updated `T`, populating only the CHANGED fields. Not scoped, no use case yet; the open question is per-field equality without reflection (many real `F` types aren't `comparable` in Go's strict sense). |
| [Validated Value Containers — `Getter`/`Setter`, `Const`, `Immutable`](validated-const-getter.md) | `codex` | Shipped (both phases) | A "Layer 2" family sitting on top of `Codec[T]`/`HasCodec[T]`: `codex.Getter[T]`/`Setter[T]`/`GetterSetter[T]` minimal interfaces (`codex/getter.go`), `codex.Const[T]`/`MustConst` (compile-time-authored constants, eagerly validated, panics if invalid) and `codex.Immutable[T]`/`NewImmutable` (runtime "set exactly once" cells — config/env-var-at-startup use case — mutex-guarded, `Set` returns a typed error, `Get` panics before first `Set`, `TryGet` for safe access) in `codex/const.go`. Both connect to `Codec[T]` at exactly one point: validating via the SAME `Codec.Validate` every other part of go-codex already uses. Phase 2: `examples/go-edge-models`'s `usecase` package adopted `Const[string]`/`codex.Template[T]` for its path patterns (three of the six substitute vars via `Template.Build` + `codex.IdentityField`/`RequiredField`), superseding an earlier bespoke typed-wrapper design. |
| [Reloadable Value Containers — `Mutable`, `NewConst`](reloadable-value-containers.md) | `codex`, `stats` | Design complete | Follow-on to the now-shipped `Const`/`Immutable` family — `codex.Mutable[T]` (a `GetterSetter[T]` cell that can be `Set` MORE than once, each call re-validated, last-good-value-wins on an invalid `Set`, `Get()` never panics) driven by key/credential rotation (JWKS, rotating API keys) for `SecurityFunc`/`CredentialFunc` closures, which are entirely BYOK today with no ready-made thread-safe cell; `codex.NewConst[T]` (non-panicking sibling to `MustConst`) falls out of `Mutable`'s own fallible construction. New `stats.ReloadObserver` extension. Biggest open question: `codex` currently has zero dependency on `stats` (which depends on `codex`) — needs resolving before implementation. |
| [`codex.Maybe[T]`: Definitive Presence Tracking](maybe-value.md) | `codex` | Design complete, awaiting decision | A lightweight, per-field alternative to `OmitEmptyField`'s zero-value HEURISTIC — go-codex's Go rendering of Haskell's `Maybe`/Rust's `Option`: `Just`/`Nothing` constructors, `Get`/`Set`/`IsSet`/`TryGet`, plus `Map`/`OrElse`/`Filter` combinators, paired with a new `MaybeField` constructor that omits a Struct field's key based on `IsSet()` DIRECTLY instead of comparing to the zero value — resolves the "never touched vs. deliberately set to zero" ambiguity `OmitEmptyField` cannot. Includes a full pros/cons discussion of `PartialField`'s pointer-based approach as an alternative (surfaces a REAL, already-shipped ambiguity: `OptionalField`+`Nullable` can't distinguish "absent" from "explicit null" either) and flags two Phase 2 ideas: `OptionalMutable[T]` (a `Mutable[T]` that may start unset) and a three-state `Maybe[Nullable[T]]` composition (RFC 7396 JSON Merge Patch shape). Explicitly NOT an alternative to the also-unimplemented `Mutable[T]` (see the doc's comparison table): `Mutable[T]` is about a value's currentness over time (always valid, hot-reloadable); `Maybe[T]` is about a value's provenance at a point in time (was it ever assigned). Two open decisions before implementation: does `Maybe[T]` need its own codec/validation, and does it need a mutex. |
| [Cache Template Parity + `Cacheable[T]`](cache-parity-and-cacheable.md) | `ports`, `adapters/redis`, `codex` | Design complete | Part 1: `ports.Cache` was not included in the rest/events/reqreply/File/Dir template-unification pass — `BuildKey`/`ValidateKeyVars` hand-roll substitution instead of delegating to `codex.BuildFromParams`, and Cache is the only boundary missing a reusable-shape escape hatch (`CacheKeyTemplate`+`NewCacheFromKeyTemplate`); both fixes are small, precedented, and transparent to `adapters/redis`. Part 2: `codex.Cacheable[T]`, a 4th sibling to `Const`/`Immutable`/`Mutable` (builds on that doc's `Mutable[T]`) adding a TTL/explicit-`Invalidate()` validity window to an in-process single-value cell, plus a follow-up Redis-backed `adapters/redis.Cacheable[T]` sibling (same shape, ctx-aware/fallible `Get`, backed by an actual Redis entry via `ports.Cache`) so a value's storage is pluggable — in-memory or Redis — without changing how callers read it. Introduces `codex.FreshGetter[T]` to resolve the `Get() (T, bool)` vs. `Getter[T]` mismatch. |
| [`ports.RefreshingCacheable[T]`](refreshing-cacheable.md) | `ports`, `codex`, `stats` | Design complete | Auto-refresh wrapper COMPOSING `codex.Cacheable[T]` (not modifying it) — `GetOrRefresh(ctx) (T, error)` single-flights a caller-supplied `RefreshFunc[T]` when stale, mirroring `adapters/nethttp.NewCachingCredentialFunc`'s existing hand-rolled single-flight/TTL pattern but generalized beyond HTTP credentials. Stale-while-revalidate is the default failure policy (`WithFailHardOnRefreshError` opts into fail-hard). Explicitly sequenced as Phase 3 — depends on `Cacheable[T]` (previous roadmap row) shipping first; a forward-looking note flags it as a candidate to later compose either the in-memory or Redis-backed `Cacheable[T]` sibling interchangeably. |
| [Streaming Walk Adapter for Files & Directories](dir-walk-adapter.md) | `adapters/file` | Idea only | Follow-on to the now-SHIPPED Directory Listing Port (`ports.Dir`/`DirEntry`, see `docs/features/ports.md`) — sketches a `ports.SourceAdapter`-shaped adapter that WALKS/streams `ports.DirEntry` values (recursive tree enumeration and/or continuous change-watching) instead of `ports.Dir.List`'s one-shot slice. Not designed: the central open question is a real dependency/architecture fork — stdlib-only polling (extends `adapters/file.WatchAdapter`'s existing approach) vs. event-based OS-native notifications (would require the FIRST external dependency in `adapters/file`, most likely `fsnotify/fsnotify`) — plus one-shot walk vs. continuous watch scope, and whether modify/delete events (not just creations) are needed. |

## How to read these plans

Each plan page covers:

- **Motivation** — why this feature belongs in go-codex
- **Scope decisions** — what is in and out of Phase 1
- **API surface** — exact type signatures, options structs, interface definitions
- **Structured errors** — every new error type with `slog.LogValuer` attributes
- **Observer integration** — which observer hooks fire and when
- **AsyncAPI / OpenAPI spec** — how the feature integrates with spec generation
- **Files to create** — concrete file list with responsibilities
- **Usage sketch** — end-to-end code example
