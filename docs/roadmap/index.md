# Roadmap — Features in Planning

This section contains implementation plans for features that have been fully researched and architecturally specified but are not yet implemented. Each page captures the design intent, API surface, error model, and key decisions so that implementation can start without re-doing the research.

These are **living design documents** — they reflect the current best thinking at the time of writing. API surface may change slightly during implementation as new constraints are discovered.

| [Request/Event Correlation ID](request-correlation-id.md) | `stats` (+ every adapter) | Idea only | A first-class, cross-cutting correlation ID for logs/metrics/support, spun out of reviewing `reqreply-workflow-simplification.md`'s wire-level `corrID`. Confirmed via code: no such concept exists anywhere today — `stats.Observer`'s own methods (`RecordRequest`/`RecordSubscribe`/`RecordPublish`) take no `ctx` at all, so they structurally can't read one even if ctx-stored. Proposes `stats.WithRequestID`/`RequestIDFromContext`/`NewRequestID`, mirroring `WithObserver`/`ObserverFromContext` exactly. **Key design question resolved**: this ID must stay DELIBERATELY SEPARATE from `TraceObserver`'s distributed trace/span ID and from reqreply's own wire-level `corrID` — three distinct concepts, not one. Whether `Observer` needs a NEW additive `RequestIDObserver` extension (mirroring `DispositionObserver`'s pattern) is flagged, not locked — needs a throwaway prototype. `ports.File`/`Cache`/`SQL`/`Dir` coverage is explicitly flagged open (same structural point as `protocol-native-features.md`'s Review-7), not force-included. |
