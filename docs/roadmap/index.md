# Roadmap — Features in Planning

This section contains implementation plans for features that have been fully researched and architecturally specified but are not yet implemented. Each page captures the design intent, API surface, error model, and key decisions so that implementation can start without re-doing the research.

These are **living design documents** — they reflect the current best thinking at the time of writing. API surface may change slightly during implementation as new constraints are discovered.

All Phase 2+ for implementation, but no longer vague — see "Coverage across every API/port boundary" in the doc. **L1-L14 ALL RESOLVED** across three full critical review passes (see prior summaries in doc history). L12 — MCP's observability resolution used to scan `mws` for a `stats.Observer`-typed `Fn` and take the FIRST match only, silently dropping a second attached observability middleware — fixed by collecting ALL matches and combining them via the EXISTING `stats.NewFanout` (discovered during Phase 1 implementation that this fan-out helper already ships in `stats`, so no new type was needed). L13 — `middleware.ContextField[V]`'s Set/Get contract (`Set` returned a NEW ctx) was incompatible with L4's finalized security `Fn` signature (no ctx in the return tuple) — fixed by redesigning `ContextField` around a pre-allocated MUTABLE BOX in ctx (mirrors `WithResponseHeaders`' exact pattern), working uniformly from EVERY `Fn` shape and even gaining bidirectional visibility. See the doc's "Known limitations and open risks" section for the full, now fully-resolved punch list. |

SSE is explicitly out of scope, blocked on confirmed missing prerequisites. Cookie attributes + an API-key example fully worked out. A further review established an explicit GUIDING PRINCIPLE: middleware, as a whole, is fundamentally a spec-layering mechanism — a declare-time value attached via `.Use(...)` that can layer into the final spec and/or have runtime dispatch behavior; "non-spec-adding" middleware (Observer, wrapping-shaped, security-shaped-unpaired) is simply the case where the spec column is empty, not a separate mechanism — stated as governing REST/events middleware today AND any future `ports` middleware design. Under this principle, `Middleware[In,Out]` retains BOTH halves of every declared param (spec metadata AND merge field), definitively resolving the previously-flagged "declare twice, no conflict check" gap as a natural consequence rather than a bolted-on fix; a `PathPrefix`/`TopicPathPrefix` sketch demonstrates the model's spec-only mirror-image case (composition semantics left open). `middleware.ContextField` confirmed to compose for free on REST. **A further critical review traced the design's proposed dispatch points against the real dispatch code and found 6 NEW open questions**: pre-handler-only timing (middleware `Out` can never depend on the handler's own result — N1/N7), `ErrorPattern` ineligibility for middleware `fn` errors (N2), an unspecified 3-tier client-side precedence (route-derived vs. middleware-derived — N3), a MANDATORY implementation requirement to avoid regressing the just-fixed duplicate-spec-param bug (N4), missing Observer/stats integration (N5), and no rule for multiple `Middleware[In,Out]` on one route (N6) — none resolved, recorded for a future Refine pass. **A feasibility analysis for the long-term goal of extending this to `ports` confirmed it is realistic**: `ports` already has the exact reusable generic param constructors (`NewCacheKeyParam`/`NewFilePathParam`) this design's whole approach depends on; Pattern-bound ports can delegate `.Use()` straight to their underlying Route/Channel, Pattern-less ports (File/Cache/Dir) need `.Use()`/dispatch wiring plus a `ctx` parameter added to `Read`/`Write`, and `ports.SQL` is a confirmed metadata-only exception needing its own design. A dedicated evaluation against net/http's/chi's own middleware model settled `Middleware[In,Out]`'s exact scope: `HandleMiddleware`'s `fn` now receives BOTH the route's own already-decoded `req *Req` (enrichable, mirrors the proven security-shaped Fn precedent) AND its own codec-backed `In` (for header/cookie/query values the route's `Req` doesn't model) — deliberately with no raw `*http.Request` anywhere, a stricter, fully-codec-defined position than net/http's/chi's own convention. A follow-up round found a real gap: `Transform`'s `fn` signature forces the concrete `Req` into its own Go type, so the SAME `fn` value can't be reused across routes with different `Req` types (confirmed: the same constraint the shipped security-shaped Fn already has) — fixed by splitting the attachment point: `Transform`/`ClientTransform` (renamed from `HandleMiddleware`/`ClientMiddleware`) for route-BOUND concerns needing `req`/`msg` access, and a widened `.Use(mw)` (via new `WithReceive`/`WithSend` methods bundling a `Req`/`T`-free Fn directly onto `Middleware[In,Out]`) for route-AGNOSTIC concerns, reusable verbatim across many routes — adopting the ALREADY-EXISTING `nethttp.Transform` name rather than inventing new vocabulary. A further round confirmed SSE's and events' previously-stated blockers are NOT fundamental — SSE gets its OWN `TransformSSE`/`ClientTransformSSE` (mirroring `Transform`/`ClientTransform`, with `SSERouteHandle` gaining response merge fields and `consumeSSE` gaining a new recognized Fn shape), and events RESOLVES its naming question by adopting `Transform`/`ClientTransform` too — delivering ONE consistent attachment vocabulary across `Route`, `SSERoute`, and `Subscriber`/`Publisher`, the explicit "simple, declarative, consistent" goal. **All 7 open design questions are now resolved** (D1-D7): pre-handler-only timing stays as-is (D1); middleware `fn` errors become `ErrorPattern`-eligible, falling back to a new `rest.MiddlewareError` instead of the semantically-wrong `SecurityError` (D2); client-side precedence is explicit > middleware-derived > route-derived (D3); the duplicate-param-layering guard is a mandatory implementation requirement (D4); Observer integration is added, improving on the legacy mechanism's silence (D5); `Declaration.Name` uniqueness is now ENFORCED per route/channel via a new `rest.DuplicateMiddlewareNameError`, deliberately diverging from the legacy mechanism's looser precedent (D6); and combining both attachment styles on one `Middleware[In,Out]` value is rejected as ambiguous via a new `rest.AmbiguousMiddlewareAttachmentError` (D7). A final pre-implementation review confirmed D2/D3/D5 now explicitly extend to events too (ChannelHandle.ErrorResponseFor/events.MiddlewareError; stats.Observer, already pattern-agnostic; the same 3-tier precedence via each adapter's own explicit-override mechanism), closing a gap where the consistency goal wasn't fully carried through the D1-D7 pass. **Extended the `PathPrefix`/`TopicPathPrefix` sketch with a third, `ports.FilePathPrefix`/`DirPathPrefix` driver** (a workspace-folder root prefix — confirmed neither `File` nor `Dir` has a general root-prefix mechanism today, `Dir.WithBaseDir` being narrower than it sounds, glob-scan-only) — surfacing a refinement the guiding-principle table doesn't fully capture: REST/events render this shape as a spec effect because path/topic IS the spec; ports render the identical "declare-time-only, resolved-once" shape as a config effect since no spec exists. Supersedes [Common-Base + Per-Pattern-Derived Middleware Types](common-middleware-architecture.md); complementary to (not competing with) [Protocol-Native Feature Declarations](protocol-native-features.md). |
