# Roadmap — Features in Planning

This section contains implementation plans for features that have been fully researched and architecturally specified but are not yet implemented. Each page captures the design intent, API surface, error model, and key decisions so that implementation can start without re-doing the research.

These are **living design documents** — they reflect the current best thinking at the time of writing. API surface may change slightly during implementation as new constraints are discovered.

An initial design (an open `Feature` interface + string-ID `Provider.Supports` check) was REJECTED mid-round — it could only reject mismatches at RUNTIME, violating a hard requirement that this redesign not compromise on Go compile-time errors anywhere. **Current mechanism: sealed, per-adapter `Capability` interfaces** (mirroring `ports.Pattern`'s own unexported-marker-method technique, applied PER ADAPTER instead of per-core-package), with capabilities supplied at `Attach`/bind time — NOT baked into a channel/route's own declared type. | [SSE Resume & Retry Policy](sse-resume-and-retry-policy.md) | `adapters/nethttp`, `adapters/chi`, `api/rest` | Findings only — no proposal, no driver yet | Spun out from SSE Client Consumption's "Out of scope" (that roadmap doc's Phase 1 shipped and was removed after a `review-go-codex` pass confirmed zero gaps against its committed scope — see `docs/design/d-0001-rest-middleware-workflow-simplification.md`'s addendum for the design lineage) once investigation showed BOTH `Last-Event-ID` resume and pluggable retry policy are genuinely client+SERVER features, not client-only follow-ons — confirmed via code that the SSE writer never emits `id:`/`event:`/`retry:` protocol fields anywhere today (only bare `data:` lines), and `stream.BroadcastHub` has no past-event buffer for any replay mechanism. Sketches two INDEPENDENT sub-features: (A) `Last-Event-ID` resume — server assigns+writes per-event `id:`, buffers recent events, replays from an incoming `Last-Event-ID` header; client tracks+resends the last-seen id on every reconnect. (B) pluggable retry policy — TWO DISTINCT halves: a client-side `RetryPolicy` func for go-codex's own `Consume`/`CallSSEAdapter`, and a server-side `retry:` field emission that spec-compliant browser `EventSource` clients honor natively, independent of go-codex's client machinery entirely. Cross-references `webhook-adapter.md`'s identical-shaped `RetryPolicy` idea as a precedent, while flagging the semantics differ (SSE reconnect is naturally infinite; webhook delivery is finite/give-up-eventually) — explicitly does NOT assume one shared type serves both without investigation. ## How to read these plans

Each plan page covers:

- **Motivation** — why this feature belongs in go-codex
- **Scope decisions** — what is in and out of Phase 1
- **API surface** — exact type signatures, options structs, interface definitions
- **Structured errors** — every new error type with `slog.LogValuer` attributes
- **Observer integration** — which observer hooks fire and when
- **AsyncAPI / OpenAPI spec** — how the feature integrates with spec generation
- **Files to create** — concrete file list with responsibilities
- **Usage sketch** — end-to-end code example
