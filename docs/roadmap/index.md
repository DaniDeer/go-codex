# Roadmap — Features in Planning

This section contains implementation plans for features that have been fully researched and architecturally specified but are not yet implemented. Each page captures the design intent, API surface, error model, and key decisions so that implementation can start without re-doing the research.

These are **living design documents** — they reflect the current best thinking at the time of writing. API surface may change slightly during implementation as new constraints are discovered.

| [Dynamic Port Rebinding (Hot-Swap Adapters)](dynamic-port-rebinding.md) | `ports` | Design draft | Live adapter cutover on running ports without process restart. REST/events/reqreply's immutable `RouteHandle`/`ChannelHandle` middleware hot-swap remains an acknowledged gap in both docs, not yet designed. |
| [Declarative Middleware](declarative-middleware.md) | `middleware` (new), `route`, `stats`, `api/rest`, `adapters/nethttp`, `adapters/chi`, `ports` | **Phase 1 (REST) SHIPPED** (security, observability, general param spec contribution — see the doc's own "Implementation status"); **Revision 2 — the declare/implement split — PLANNED, approved, not yet implemented** (splits `middleware.Middleware` into pure declare-time data + a new register-time `ServerImplementation`, removing `RequireScopes`/`RequireAPIKey`/`ObservabilityMiddleware`'s old bundled shape entirely; relocates the security coverage check to adapter `Register`/`Handler` time; adds `nethttp.Caller`); `ports.File` decorator shapes (Read AND Write) sketched and proven, ready to implement for Phase 2 | Core thesis: routes/channels/ports should reduce to pure input/output, with cross-cutting concerns attached externally via ONE shared, composable `middleware.Middleware` mechanism. TWO ATTACHMENT POINTS resolve a sequencing bug (spec generation freezes at `.Register(builder)`, before a transport-layer-attached middleware could ever influence it): spec-relevant middleware (carrying a `Security`/`RequestParams`/`ResponseParams` declaration) attaches via a NEW `rest.WithMiddleware` `RouteOpt` at `NewRoute(...).Register(builder)` time — EARLY enough to feed the OpenAPI spec directly, so a route needs ZERO manual `WithSecurityScheme`/`RouteMeta.Security`/header-param calls; non-spec/shared middleware (observability, logging) stays attachable at `nethttp.Register(...)`'s variadic parameter, unchanged. This is NOT the previously-rejected "infer from attached middleware" — the middleware VALUE carries a COMPLETE, EXPLICIT declaration (scheme, scopes, codec, via ordinary constructor arguments); attaching it IS declaring it, cross-checked for conflicts (`ConflictingSecurityDeclarationError`) against the still-supported manual escape hatch. Security `Fn` is Req-generic AND POINTER (`*Req`) — reads AND WRITES the already-merged struct, closing a "declare twice" gap; `codex.DecodeVars`/`RequiredField`/`OptionalField` let a middleware decode via ITS OWN dedicated codec with zero new `codex` API (with an explicit guardrail: a VERIFYING codec must never be wired through a route-declared merge field — it renders the WRONG OpenAPI schema, confirmed via `codex.StringValidatorFrom`). New `middleware.ContextField[V]` — a codec-typed ctx value bus mirroring `WithResponseHeaders`/`stats.WithObserver` — is the default recommendation for TRULY cross-cutting data (keeps Req/Resp security-agnostic). Response-side header/cookie forwarding already works via existing `WithResponseHeaders`/`WithResponseCookies`; `ResponseParams` adds the spec-declaration half. Observability: `stats.Observer` splits into boundary-shaped (moves to middleware, zero loss) vs. decode-intrinsic (`RecordValidationError`, resolved via a new `stats.Diagnostic` ctx-ferry) — `nethttp.ObservabilityMiddleware` becomes the sole remaining `stats.Observer` call site, `Options.Observer` REMOVED. Will get a dedicated `docs/concepts/middleware.md` + `docs/features/middleware.md` doc pair once implemented. **Coverage confirmed for every LAYER 2 boundary go-codex ships** (exactly THREE attachment shapes — HTTP/message/decorator — no fourth needed anywhere): events/reqreply (`mqtt`/`mqtt5`/`zeromq`) get FULL parity with REST (message-shaped, reusing the SAME `stats.Diagnostic` ferry); MCP (`mcpgo`) gets observability-only via a decorator shape (Security stays permanently N/A, unchanged); `ports.File`/`Cache`/`SQL`/`Dir` all get the SAME decorator shape `File` already proves. Layer 3 (`forge.Registry`/pipelines) is NOT covered — see L14 below. All Phase 2+ for implementation, but no longer vague — see "Coverage across every API/port boundary" in the doc. **L1-L14 ALL RESOLVED** across three full critical review passes (see prior summaries in doc history). L12 — MCP's observability resolution used to scan `mws` for a `stats.Observer`-typed `Fn` and take the FIRST match only, silently dropping a second attached observability middleware — fixed by collecting ALL matches and combining them via the EXISTING `stats.NewFanout` (discovered during Phase 1 implementation that this fan-out helper already ships in `stats`, so no new type was needed). L13 — `middleware.ContextField[V]`'s Set/Get contract (`Set` returned a NEW ctx) was incompatible with L4's finalized security `Fn` signature (no ctx in the return tuple) — fixed by redesigning `ContextField` around a pre-allocated MUTABLE BOX in ctx (mirrors `WithResponseHeaders`' exact pattern), working uniformly from EVERY `Fn` shape and even gaining bidirectional visibility. L14 — `forge.Registry`/pipelines (Layer 3) were never checked against this design at all despite the doc's "every boundary" claim — resolved by spinning the question out into a new dedicated roadmap doc, [Forge Pipeline Middleware](forge-pipeline-middleware.md), rather than deciding inline; this doc's own coverage claim now explicitly scopes itself to Layer 2 only. See the doc's "Known limitations and open risks" section for the full, now fully-resolved punch list. |

| [`codex.OptionalMutable[T]`: A Mutable Cell That May Start Unset](optional-mutable.md) | `codex`, `stats` | Design draft — `Mutable[T]` now shipped, ready to implement | `Mutable[T]`'s revalidating, hot-reloadable `Set` + `Maybe[T]`'s "may start unset" lifecycle, combined into a standalone THIRD type (not a modification of either) — for an optional feature's rotating credential that might not exist until the feature is enabled. Reuses `Mutable[T]`'s `codex.ReloadObserver` unchanged; `Get()` never panics (returns zero value if never `Set`, mirroring `Maybe[T]`'s precedent, not `Immutable[T]`'s panic-before-first-`Set`). Was explicitly sequenced AFTER `Mutable[T]` ships — that dependency is now satisfied — promoted from a one-line flagged idea once the need surfaced twice. |
| [`Mutable[T]`/`Cacheable[T]` — Subscribe-to-Changes](mutable-native-integration.md) | `codex` | Idea only — no driver | Of the 3 ideas this doc originally captured, 2 are now RESOLVED with no code change: native Builder security wiring (`SecurityFunc`/`CredentialFunc` are already plain closures — a caller composes `Mutable[T]`/`Cacheable[T]` via `.Get()` with zero new API, proven in `examples/mutable-security-keys` and documented in `docs/concepts/codec.md`'s "Composing with adapters" subsection), and folding `adapters/nethttp.NewCachingCredentialFunc` onto a container (redirected to `ports.RefreshingCacheable[T]`, not `Mutable[T]` — revisit after that ships). Only a "subscribe to changes" push-notification mechanism (distinct from `ReloadObserver`/`InvalidateObserver`, which only cover observability) remains open, with no driver and a genuinely open design space (channel-sub vs. callback vs. `stream.Stream[T]`). |
| [`Maybe[Nullable[T]]` (Three-State Fields)](maybe-nullable-and-codec.md) | `codex` | Idea only | A three-state field (absent/present-null/present-value — the RFC 7396 JSON Merge Patch shape) via `Maybe[Nullable[T]]` — VERIFIED to already compose for free with zero new code (`MaybeField("x", codex.Nullable(inner), ...)` on a `Maybe[*T]` field genuinely distinguishes all three states today); what's left is documentation-only (a worked example + test). (This doc's other idea — a public `codex.Codec[Maybe[T]]` — has SHIPPED as `codex.MaybeCodec[T]`, see `docs/concepts/codec.md`'s "`Maybe[T]`: definitive presence tracking" subsection.) |
| [`Cacheable[T]`: Redis-Backed Sibling](cacheable-redis-backed.md) | `adapters/redis`, `codex`, `ports` | Design draft — `codex.Cacheable[T]` now shipped, ready to implement | Follow-on to the now-SHIPPED in-process `codex.Cacheable[T]` (see `docs/concepts/codec.md`'s `Cacheable[T]` subsection and `codex/cacheable.go`) — a `adapters/redis.Cacheable[T]` sibling with the same TTL/`Invalidate()` shape but a ctx-aware, fallible `Get(ctx) (T, bool, error)` backed by an actual Redis entry via `ports.Cache`, so a value's storage is pluggable (in-memory or Redis) without changing how callers read it. Also captures a "generic multi-key `Cacheable`" idea as a no-driver-yet note. |
| [`ports.RefreshingCacheable[T]`](refreshing-cacheable.md) | `ports`, `codex`, `stats` | Design complete — `codex.Cacheable[T]` now shipped, ready to implement | Auto-refresh wrapper COMPOSING `codex.Cacheable[T]` (not modifying it) — `GetOrRefresh(ctx) (T, error)` single-flights a caller-supplied `RefreshFunc[T]` when stale, mirroring `adapters/nethttp.NewCachingCredentialFunc`'s existing hand-rolled single-flight/TTL pattern but generalized beyond HTTP credentials. Stale-while-revalidate is the default failure policy (`WithFailHardOnRefreshError` opts into fail-hard). Its `Cacheable[T]` dependency (previous roadmap row) has now shipped; a forward-looking note flags it as a candidate to later compose either the in-memory or Redis-backed `Cacheable[T]` sibling interchangeably. |
| [Streaming Walk Adapter for Files & Directories](dir-walk-adapter.md) | `adapters/file` | Idea only | Follow-on to the now-SHIPPED Directory Listing Port (`ports.Dir`/`DirEntry`, see `docs/features/ports.md`) — sketches a `ports.SourceAdapter`-shaped adapter that WALKS/streams `ports.DirEntry` values (recursive tree enumeration and/or continuous change-watching) instead of `ports.Dir.List`'s one-shot slice. Not designed: the central open question is a real dependency/architecture fork — stdlib-only polling (extends `adapters/file.WatchAdapter`'s existing approach) vs. event-based OS-native notifications (would require the FIRST external dependency in `adapters/file`, most likely `fsnotify/fsnotify`) — plus one-shot walk vs. continuous watch scope, and whether modify/delete events (not just creations) are needed. |

## How to read these plans

Each plan page covers:

- **Motivation** — why this feature belongs in go-codex
- **Scope decisions** — what is in and out of Phase 1
- **API surface** — exact type signatures, options structs, interface definitions
- **Structured errors** — every new error type with `slog.LogValuer` attributes
- **Observer integration** — which observer hooks fire and when
- **AsyncAPI / OpenAPI spec** — how the feature integrates with spec generation
- **Files to create** — concrete file list with responsibilities
- **Usage sketch** — end-to-end code example
