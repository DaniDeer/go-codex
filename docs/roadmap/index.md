# Roadmap — Features in Planning

This section contains implementation plans for features that have been fully researched and architecturally specified but are not yet implemented. Each page captures the design intent, API surface, error model, and key decisions so that implementation can start without re-doing the research.

These are **living design documents** — they reflect the current best thinking at the time of writing. API surface may change slightly during implementation as new constraints are discovered.

This is NOT the previously-rejected "infer from attached middleware" — the middleware VALUE carries a COMPLETE, EXPLICIT declaration (scheme, scopes, codec, via ordinary constructor arguments); attaching it IS declaring it, cross-checked for conflicts (`ConflictingSecurityDeclarationError`) against the still-supported manual escape hatch. Security `Fn` is Req-generic AND POINTER (`*Req`) — reads AND WRITES the already-merged struct, closing a "declare twice" gap; `codex.DecodeVars`/`RequiredField`/`OptionalField` let a middleware decode via ITS OWN dedicated codec with zero new `codex` API (with an explicit guardrail: a VERIFYING codec must never be wired through a route-declared merge field — it renders the WRONG OpenAPI schema, confirmed via `codex.StringValidatorFrom`). New `middleware.ContextField[V]` — a codec-typed ctx value bus mirroring `WithResponseHeaders`/`stats.WithObserver` — is the default recommendation for TRULY cross-cutting data (keeps Req/Resp security-agnostic). Response-side header/cookie forwarding already works via existing `WithResponseHeaders`/`WithResponseCookies`; `ResponseParams` adds the spec-declaration half. Observability: `stats.Observer` splits into boundary-shaped (moves to middleware, zero loss) vs. decode-intrinsic (`RecordValidationError`, resolved via a new `stats.Diagnostic` ctx-ferry) — `nethttp.Observability` becomes the sole remaining `stats.Observer` call site, `Options.Observer` REMOVED. Will get a dedicated `docs/concepts/middleware.md` + `docs/features/middleware.md` doc pair once implemented. **Coverage confirmed for every LAYER 2 boundary go-codex ships** (exactly THREE attachment shapes — HTTP/message/decorator — no fourth needed anywhere): events/reqreply (`mqtt`/`mqtt5`/`zeromq`) get FULL parity with REST (message-shaped, reusing the SAME `stats.Diagnostic` ferry); MCP (`mcpgo`) gets observability-only via a decorator shape (Security stays permanently N/A, unchanged); `ports.File`/`Cache`/`SQL`/`Dir` all get the SAME decorator shape `File` already proves. Layer 3 (`forge.Registry`/pipelines) is NOT covered — see L14 below. All Phase 2+ for implementation, but no longer vague — see "Coverage across every API/port boundary" in the doc. **L1-L14 ALL RESOLVED** across three full critical review passes (see prior summaries in doc history). L12 — MCP's observability resolution used to scan `mws` for a `stats.Observer`-typed `Fn` and take the FIRST match only, silently dropping a second attached observability middleware — fixed by collecting ALL matches and combining them via the EXISTING `stats.NewFanout` (discovered during Phase 1 implementation that this fan-out helper already ships in `stats`, so no new type was needed). L13 — `middleware.ContextField[V]`'s Set/Get contract (`Set` returned a NEW ctx) was incompatible with L4's finalized security `Fn` signature (no ctx in the return tuple) — fixed by redesigning `ContextField` around a pre-allocated MUTABLE BOX in ctx (mirrors `WithResponseHeaders`' exact pattern), working uniformly from EVERY `Fn` shape and even gaining bidirectional visibility. L14 — `forge.Registry`/pipelines (Layer 3) were never checked against this design at all despite the doc's "every boundary" claim — resolved by spinning the question out into a new dedicated roadmap doc, [Forge Pipeline Middleware](forge-pipeline-middleware.md), rather than deciding inline; this doc's own coverage claim now explicitly scopes itself to Layer 2 only. See the doc's "Known limitations and open risks" section for the full, now fully-resolved punch list. |
